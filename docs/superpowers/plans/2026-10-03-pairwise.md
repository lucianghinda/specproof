# Finite pairwise coverage implementation plan

**Goal:** Derive and observe feasible two-input combinations from explicit finite domains, including declarative forbidden assignments.

**Architecture:** Preserve scalar defaults. Add immutable joint-domain metadata to Specification and a bounded finite-space analyzer shared by checking, planning, reporting and observation. Reuse the existing full-tuple collector; do not replay tests or retain an event trace.

**Stack:** Existing Ruby standard library, optional existing RBS and Minitest. No new dependencies.

## Accepted syntax and semantics

```ruby
SpecProof.define "DeliveryOptions#build" do
  input :expedited, values: [false, true]
  input :notify, values: [false, true]
  combinations :expedited, :notify, all_allowed: true
end

SpecProof.define "ConstrainedDelivery#build" do
  input :expedited, values: [false, true]
  input :notify, values: [false, true]
  combinations :expedited, :notify do
    forbid expedited: true, notify: false
  end
end
```

One group per target, at least two unique nonempty Symbol names, each an analyzed finite input. Group may select a subset of analyzed inputs; every analyzed input still validates before any hit. Exclusions cannot be group members. DSL order does not matter. For RBS composition, a combinations-only DSL declaration is valid when RBS supplies the named finite inputs; without supplied types it is invalid. RBS string import remains unsupported.

Use either `all_allowed: true` without a block or a block with at least one `forbid`; reject false, ambiguous/missing modes, duplicate groups, unknown options and empty blocks. Each forbid is a nonempty keyword assignment using group names and supported primitive values belonging to those input domains. A clause matches all its assignments; matching any clause forbids the tuple. Partial clauses constrain every completion. Rules are data, never predicate blocks. Copy/freeze all metadata and retain declaration/rule provenance. Duplicate equivalent rules may be deduplicated for identity while preserving all contributing sources.

Malformed declarations are configuration errors (CLI exit 2); a well-formed group with no allowed complete assignment is a semantic finding `unsatisfiable_combinations` (check/plan exit 1, no plan). Do not silently infer intent or drop restrictions. Unary clauses and jointly unreachable individual values are allowed; scalar candidates remain declared marginal candidates, and no reachability claim is added for them.

`pairwise-finite-v1` is opt-in via `SpecProof.plan(..., criterion:)`, `specproof plan ... --criterion pairwise-finite-v1`, and `Minitest.install!(criterion: "pairwise-finite-v1", ...)`. CLI `check` remains criterion-independent and rejects `--criterion`. A pairwise plan requires a group for every supplied target; never silently skip a target. Default remains `input-basics-v1`.

A pair is required exactly when at least one allowed full group assignment contains it. Distinct input names form unordered pairs, names sorted canonically; values preserve their types, including string/symbol distinction. Enumerate at most 10,000 complete group assignments and at most 10,000 possible pair rows per target, checking products/counts before allocation. Reject larger spaces with `combination_limit_exceeded`; never truncate or sample. Bound total planned pair obligations to 10,000 across targets as well.

## Shared interfaces

- `Specification#combination_group` defaults to nil. `CombinationGroup` has `inputs` (sorted Symbol array), `forbidden` (ForbiddenAssignment array), `source`; `ForbiddenAssignment` has frozen `assignments` and `source`.
- `PairObligation` has `id`, `target`, `inputs` (frozen two-entry Symbol-to-value hash), `reasons`, `sources`. Scalar Obligation remains unchanged.
- `CombinationFinding` has `code`, `target`, `inputs` (group names), `sources`; serialize separately from scalar Finding, with an empty witness array for unsatisfiability.
- `CombinationSpace.new(specification)` validates group names/domains/rules and size limits; exposes `pairs`, `excluded_pairs` (arrays of two-entry value hashes), `allowed_count`, `sources` (group/input/rule provenance), `allowed?(arguments)` (joint rule check). Missing group is a configuration error for this analyzer.
- Planner defines `PAIRWISE_CRITERION` and selects scalar or pair generation after Checker. Pair IDs hash target, canonically ordered typed input assignments and criterion. Group ordering, rule ordering, source locations and duplicate rules do not change identity. Existing scalar IDs remain unchanged.
- Specification digest includes canonical group/rule metadata only when present; no-group legacy digest bytes remain unchanged. Scalar and pairwise runs can share a contract digest but must have different criterion/obligation identities.

## Runtime and reporting

Only a fully valid analyzed tuple can earn a scalar or pair hit. Joint forbidden tuples fulfill neither criterion and are recorded under existing `outside_domain`; add `outside_combinations` counts and immutable witness/source evidence when joint constraints caused rejection. Such observations do not themselves imply a broken implementation: negative tests may deliberately exercise rejection. Preserve current outside-domain exit semantics and original assertion results.

Pairwise rows serialize `inputs` as name-to-typed-value objects instead of scalar `input`/`value`; keep shared id/target/reasons/sources/status/hits. Reports disclose criterion and group input scope. Pairwise plans and runtime reports include `excluded_pairs` with target, typed inputs, `reason: "no_allowed_completion"`, and all relevant constraint sources. Excluded pairs never enter the denominator. Distinguish a forbidden full tuple from an infeasible pair: with three inputs a forbidden tuple may contain individually feasible pairs.

Human plan/runtime output prints both names and exact values for missing pairs, totals and excluded-pair counts. No-group scalar output remains compatible; also render finite string values correctly in runtime missing summaries. CLI and Minitest preparation failures must remain atomic, identify the requested criterion, and preserve actual tests_passed. All prior lifecycle, object exclusion, finite-text and exact-signature protections remain.
